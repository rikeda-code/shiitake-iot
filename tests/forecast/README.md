# 直近工数計画ダッシュボード（work-hours-forecast.html）のテスト

`dashboard/work-hours-forecast.html` の動作確認用 Playwright テストです。
DB共有シート等への実際のネットワークアクセスは行わず、`page.route()` でCSV/gvizレスポンスをモックして検証します。

## 必要なパッケージ

- Node.js
- [Playwright](https://playwright.dev/)（`playwright` パッケージと Chromium 本体）

リポジトリに `playwright` が未インストールの場合は以下でインストールしてください。

```sh
npm install -D playwright
npx playwright install chromium
```

## テストの実行方法

1. リポジトリのルートで、`dashboard` フォルダをカレントにしたローカルサーバーを起動する（別ターミナル、またはバックグラウンド実行）。

   ```sh
   python3 -m http.server 8811 --directory dashboard
   ```

2. テストを実行する（テストは `http://localhost:8811/work-hours-forecast.html` にアクセスします）。

   ```sh
   node tests/forecast/verify_forecast_shipping_sales.js
   node tests/forecast/verify_regression_consolidated.js
   node tests/forecast/verify_forecast_shipping_labor_inabe.js
   node tests/forecast/verify_forecast_shipping_labor_gunma.js
   node tests/forecast/verify_forecast_shipping_labor_nantan.js
   node tests/forecast/verify_cell_selection.js
   node tests/forecast/verify_sticky_unit_column.js
   node tests/forecast/verify_harvest_forecast_input.js
   node tests/forecast/verify_forecast_shipping_workday_shift.js
   ```

   各行末に `: OK` / `: NG` が出力され、最後に `すべてOK` / `NGあり` と `DONE` が表示されれば実行完了です。
   終了コードは成功時 `0`、失敗時 `1` です。

## ファイルの内容

- `verify_forecast_shipping_sales.js` — 出荷パネル1（販売抽出シートの実績・受注データ接続、商品分類ルール、個数の表示形式など）の検証。あわせて、基準日〜6日後の7日分＋合計列になったこと（見出しの期間表示を含む）、パック数・cs数・合計の7日分の合計、1日分欠けたときの部分合計＋「（6日分）」表示、7日分そろうと日数の注記が付かないこと、合計は丸める前の値を足してから1回だけ丸めること（0.04×7→0.3になる例）を確認する。さらに、出荷の作業は出荷日の前日に行うため、作業日（列自身の日付）Dの列には出荷日D+1のデータが入ること（パネル1・2とも）、列見出し・合計列に出荷日の注記（「出荷 M/D」「出荷 M/D〜M/D」）が小さく添えられること、実績／受注の判定が出荷日（作業日の翌日）基準になること（ユーザー指示の例「今日が10/22のとき、作業日10/21の列(出荷日10/22)は受注、作業日10/20の列(出荷日10/21)は実績」をそのまま再現して確認）を確認する。
- `verify_regression_consolidated.js` — 栽培・出荷の既存機能全般の回帰確認（複数拠点のパネル表示、スティッキーヘッダー、基準日の未来選択、描画の世代チェック、URL保持など）。あわせて、栽培の各パネル（工程件数・稼働コンテナ数、標準工数、標準労働時間）で合計列の見出し（期間表示）・7日分の合計（件数系）・収穫見込みが一部の日しか無い場合の部分合計＋「（1日分）」・収穫見込みが全く無い場合の合計「－」を確認し、出荷側で合計列の出荷数量の部分合計＋「（◯日分）」、標準労働時間合計・出勤人数（延べ人数）・過不足（標準労働時間と標準工数それぞれの合計どうしの差）・人別内訳の合計を確認する。稼働コンテナ数（その日時点の台数という状態のスナップショット値）の合計列は、7日分の延べ台数を合計した上で「延べ」の注記を添えて区別すること、稼働コンテナ数から計算される標準工数の行（コンテナ点検時間等）は今までどおり普通の7日分の合計になることを確認する。さらに、工程件数の詳細行のうち芽待ち／成長待ち・芽発生・培養（稼働コンテナ数と同じ「その日時点でその段階にある台数」という状態のスナップショット値）も同様に延べ台数の合計＋「延べ」の注記になり、コンテナ掃除・コンテナ点検（その日に行った作業の件数という出来事の積み上げ）は「延べ」の注記無しの普通の7日分の合計になることを確認する。トグル（拠点／区分）の左右のDOM順が拠点→区分であることも確認する。
- `verify_forecast_shipping_labor_inabe.js` — 出荷×いなべのパネル3（標準労働時間）をシフト表の実データに接続した機能の検証（部門「出荷」「配送・出荷」での絞り込み、シフトの値の扱い、標準労働時間シートとの照合・エイリアス・部門不一致時の未照合警告、拠点シフト表GAS経由での絞り込み、過不足の計算、シフト表の日付範囲外の扱い、南丹（出荷）も「勤務用_出荷」シートの実データに接続済みでサンプルの帯が表示されないこと、栽培/出荷の切替で部門が混ざらないこと）。あわせて、人別内訳の合計列が7日分の合計になること、シフト表の日付範囲外の日を含む場合に合計列が範囲内日数だけの部分合計＋「（◯日分）」になることを確認する。
- `verify_forecast_shipping_labor_gunma.js` — 出荷×群馬のパネル3（標準労働時間）を勤務表「出荷場」シートの実データに接続した機能、および出荷場での空欄の判断ルール（先頭の空欄は`classifyGunmaLeadingBlankPolicy()`、先頭より後の空欄は休みの印を手がかりにした`classifyGunmaMiddleBlankPolicy()`）の検証。休みの印（休・有休・夏・振休等。「入社」は含まない）の間の空欄が出勤になること、同じ月度の残りに休みの印が無い場合は次の月度（`gids`のみ対象）のシートを見て休みの印の有無で出勤／休み扱いを判断すること、次の月度が未設定・読めない場合や行が全部空欄の場合に計上せずアラートを出すこと（全部空欄の場合は既存の人かどうかより優先されること）、先頭の空欄の扱い（既存の人／新しい人／前の月度未設定）が従来どおりであること、不要なときは次の月度のシートを読み込まないこと、配送担当（吉村(出)・高橋(出)）の除外、栽培（収穫班シート）は従来どおり空行の位置で空欄を判断し影響を受けないこと、いなべは今までどおり、南丹（出荷）も「勤務用_出荷」シートの実データに接続済み（サンプル名ではなく実名で表示される）であることを確認。あわせて、休み・次の月度未設定などで0時間と確定した日は「判断できない(－)」とは区別され合計列が7日分の合計になる（日数の注記が付かない）ことを、具体的な数値（人別内訳の合計列）で確認する。

- `verify_forecast_shipping_labor_nantan.js` — 出荷×南丹のパネル3（標準労働時間）を、紙の勤務表から作成した勤務表ファイル（栽培の南丹勤務表と同じスプレッドシート、`FORECAST_SHIPPING_SHIFT_SOURCES['南丹']`）の「勤務用_出荷」シート（`datedHoursSheet`形式、26.10/11〜11/10）の実データに接続した機能の検証。読み込み・計算は栽培の南丹(`fetchNantanShiftSheets`/`classifyNantanShiftCell`/`computeNantanStandardLaborHours`。栽培・出荷で別のgidを使うため`nantanShiftSheetsCache`はgid単位）と共通の関数を使っている。「8H」「7H」「6H」「4H」「3H」が時間として数えられ出勤人数に入ること、「休」「-/法」「-/公」は0時間で出勤人数に入らないこと、シートに日付の列が無い日（11/11以降）は「－」になり合計列が範囲内日数だけの部分合計＋「（◯日分）」になること、サンプルデータの帯が表示されなくなったこと、人別内訳が実名（部門は「－」固定）で表示されること、栽培×南丹（別のgidの勤務表シート）・出荷×いなべ・出荷×群馬の結果が変わらないことを確認する。
- `verify_cell_selection.js` — 表のセルを範囲選択して画面下に集計（合計・平均・個数・最小・最大）を表示する機能の検証。ドラッグでの四角い範囲選択、Shift＋クリックでの範囲拡張、Ctrl（⌘）＋クリックでの別の表（別パネル）のセルを含む追加選択、丸める前の値（`data-raw`）を合計してから1回だけ丸めること（0.04×2セル→0.1になる例）、「－」・「計算方法未定」や補足文字（「（◯日分）」「延べ」「*」）が集計・個数に入らないこと、見出しの行・列や出荷数量の実績・受注の印の行（見出し専用行）が選べないこと、単位（`data-unit`）が混在したときの注意表示、合計列と日ごとの列を一緒に選んだときの二重計上の注意表示、Esc・表の外のクリック・基準日の切替（`render()`のたびの`clearCellSelection()`、描画の世代チェックとの整合）で選択が解除され集計帯が消えること、スマートフォン（タッチ）でタップのたびに選択に加える／外せること・合成マウスイベントと二重に反応しないこと・「選択を解除」ボタンで解除できること、既存のクリックの動き（拠点／区分トグル・基準日ボタン・詳細の開閉）が変わらないこと、栽培 標準工数 小計で日ごとに「*」が付く日があれば合計列の小計にも「*」が付くこと（収穫見込みが全日入力済みの場合は付かないこと）、栽培・出荷×いなべ・群馬・南丹の6画面すべてで3段の表（折りたたみの詳細・人別内訳を含む）に選択可能セルがあること、集計帯の高さが文字1行+最小限の余白に収まること（幅1280pxで単位混在の注意表示が出ていても帯が1行のまま高さが変わらないこと）、幅375pxで「選択を解除」ボタンが帯の高さ・画面幅に収まり押せること、注意表示の文字が省略・切り取りされないこと、帯が出ている間のページ下の余白が帯の高さ以上あることを確認する。

- `verify_sticky_unit_column.js` — 見出しの固定を「氏名」の列の幅だけ（1列目のみ）にし、上の段の表（工程件数・稼働コンテナ数、出荷数量、標準工数、標準労働時間の本体・折りたたみの詳細）の2列目を単位の列にした変更の検証。1列目（行見出し／氏名）だけが`position:sticky`で固定され、2列目（単位／部門）は日付の列と一緒に横スクロールすること（375px・1280pxの両方の画面幅で）、上の段の表の2列目に行ごとの単位（`data-unit`と同じ割り当て）が右寄せで表示され、見出し行は「単位」・単位が無い行（実績・受注の印の行など）は空欄になること、1列目に収まらない長い行見出し（「小計（栽培 標準工数合計）」「過不足（標準労働時間－標準工数）」）が省略されず折り返して表示されること、標準労働時間の本体表と人別内訳の表で日付の列（当日〜合計）の位置がそろっていること、単位の列はセル範囲選択（PR #498）の対象にならないこと・表を指で動かした（スクロール相当の）操作ではセルが選択されないこと、狭い画面（375px）で表を横スクロールしても上部固定（基準日・トグル）が横にずれないこと、栽培・出荷×いなべ・群馬・南丹の全6画面・3段すべての表（折りたたみの詳細・人別内訳を含む）で同じ動きになることを確認する。

- `verify_harvest_forecast_input.js` — 栽培の標準工数パネルに「収穫計画（kg）」の表示行と「収穫見込（入力）」の手入力欄を加え、見込kgが入っている日は収穫計画kgより優先して収穫工数を計算する変更の検証。純粋関数（`computeStandardWorkHours`の見込優先・`parseManualHarvestInput`の入力値の読み取り）、保存先GAS（`HARVEST_FORECAST_GAS_URL`）が未設定のときは入力欄が無効で計画kgだけで計算されること、GASから読んだ見込が入力欄に入り青字で計算されること、入力→即時再計算（収穫・小計・注記）とGASへの保存（拠点・日付・kg、空欄はkg:nullで削除）、数値以外は保存しないこと、保存に失敗した欄は赤くなりEnterで保存し直せることを、群馬（基準日2026/10/21）で確認する。GASのURLはページ取得時に差し替え、GETとPOSTは`page.route()`でモックする。
- `verify_forecast_shipping_workday_shift.js` — 出荷パネル1・2を「作業日Dの列に出荷日D+1のデータを表示する」表示に変更した機能の検証（`verify_forecast_shipping_sales.js`・`verify_regression_consolidated.js`と内容が重複しない部分を中心に確認）。基準日が今日以外のときも列見出し・合計列の出荷日注記（個別・合計、パネル1・2とも）が作業日+1日で正しく計算されること、列自身の日付（作業日の見出し・合計範囲）は従来どおり変わらないこと、パネル3（標準労働時間）は列の日付（作業日自身）のまま変わらないこと（曜日ごとに異なる労働時間のモックで確認）、過不足（パネル2とパネル3の比較）が同じ列番号どうしで比較されること（列自身の日付のダミー値と出荷日の正しい値を区別できるようモックし、誤って列自身の日付を使うと異なる値になってしまう例で確認）、栽培タブの画面・計算は変更されていないことを確認する。

いずれのファイルも、CSVモックの組み立てや日付固定（`fixTodayTo`）などの補助関数をファイル内に直接含んでおり、他ファイルへの依存はありません。

## 公開対象からの除外について

`tests/forecast/` は GitHub Pages（`.github/workflows/pages.yml` の `upload-pages-artifact` が `dashboard` フォルダのみを対象にしている）および Firebase Hosting（`firebase.json` の `hosting.public` が `dashboard` のみを指している）のどちらからも、もともと対象外です。追加の除外設定は不要でした。

GitHub Actionsの `validate` ジョブ（`pages.yml`）は `dashboard/*.html` のみを対象にJS構文チェックを行うため、`tests/forecast/` 配下のファイルで失敗することはありません（テストを自動実行する設定にもなっていません）。
