# 勤務時間ダッシュボード（work-hours.html）のテスト

`dashboard/work-hours.html` の動作確認用 Playwright テストです。
実際のスプレッドシートへのネットワークアクセスは行わず、`page.route()` で `/export` 系リクエストを
空のCSVで応答させるだけにとどめ、ページの読み込み自体は素早く失敗させます（`tests/forecast/`・
`tests/shipment-plan/` のように実データ構成に合わせたCSVモックは組みません）。
ただし `verify_shipping_actual_auto.js`・`verify_remove_prod_sheet.js` は、生産実績データの
組み立てをページ全体の読み込み（`fetchProductionSheet()`）から各画面の表示まで通して確かめるため、
実際のシートの構成に合わせたモック（整理済み_M・整理済み_計画_更新のgviz、DB共有の
「URL_収穫管理表」「URL_売上分析」「販売抽出シート(商品別)」・各拠点の収穫管理表・売り上げ分析・
販売抽出シートの実績タブ・菌床数集計・標準工数設定のCSV）を組みます。整理済み_分析（廃止済み）の
モックは用意せず、読みに行った場合は記録して「読みに行かないこと」を確認します。

work-hours.html はIIFEで包まれていないトップレベルのスクリプトのため、ページを開くだけで
`fitChartHeightForTooltip`・`fitSegmentLabelChartHeight`・`computeSegmentLabelChartHeight` が
`window` 直下の関数として使えます。この性質を利用し、「予実＞比較（繁忙期見込み）」タブの各グラフが
実際に使っているのと同じ形（Chart.js 4.4.3、`interaction:{mode:'index',intersect:false}`、
積み上げ棒＋行ごとの label/afterLabel/footer コールバック）のテスト用チャートを直接作り、
本物のChart.jsに実測させる形で確認します（画面上の拠点・月・トグル操作を実際にクリックして辿る
E2Eテストではなく、新設した高さ決定ロジックを本物のChart.jsに対して直接検証するテストです）。

Chart.js本体（CDN: `cdn.jsdelivr.net`）はテスト実行環境のネットワーク事情に左右されないよう、
`vendor/chart.umd.js`（npmの `chart.js@4.4.3` から複製。work-hours.html が読み込むバージョンと
同じ）に差し替えます。

## 必要なパッケージ

- Node.js
- [Playwright](https://playwright.dev/)（`playwright` パッケージと Chromium 本体）

リポジトリに `playwright` が未インストールの場合は以下でインストールしてください。

```sh
npm install -D playwright
npx playwright install chromium
```

## テストの実行方法

1. リポジトリのルートで、`dashboard` フォルダをカレントにしたローカルサーバーを起動する（別ターミナル、
   またはバックグラウンド実行）。`tests/forecast/`（8811番）・`tests/shipment-plan/`（8812番）が
   同時に使うポートとは別の8813番を使う。

   ```sh
   python3 -m http.server 8813 --directory dashboard
   ```

2. テストを実行する（テストは `http://localhost:8813/work-hours.html` にアクセスします）。

   ```sh
   node tests/work-hours/verify_plancompare_tooltip_height.js
   ```

   各行末に `: OK` / `: NG` が出力され、最後に `すべてOK` / `NGあり` と `DONE` が表示されれば実行完了です。
   終了コードは成功時 `0`、失敗時 `1` です。

   ```sh
   node tests/work-hours/verify_sitesummary_headcount_labels.js
   ```

   ```sh
   node tests/work-hours/verify_sitesummary_headcount_total.js
   ```

   ```sh
   node tests/work-hours/verify_shipping_actual_auto.js
   ```

   ```sh
   node tests/work-hours/verify_remove_prod_sheet.js
   ```

## ファイルの内容

- `verify_plancompare_tooltip_height.js` — 「予実＞比較（繁忙期見込み）」タブの各グラフ
  （拠点・業務別 `plancmp2-*`、拠点サマリ `plansitesum2-*`、3拠点サマリ `plansum2-*`、
  要員計画 `planstaffplan2-*`。「表」サブタブはグラフが無いため対象外）に適用した、
  ツールチップ（`mode:'index'` でキャンバス内に描かれる窓）が高さに収まらず下の行が
  切れないようにする仕組み（`fitChartHeightForTooltip()`）の検証。表示中の各月のうち
  最も内容が多い月のツールチップの高さ（Chart.js自身の計算結果を実測。行数や1行の高さを
  決め打ちで見積もっていないこと）がグラフの高さを上回る場合だけ高さが広がり、収まって
  いる場合は今の高さ（固定320px・420px、または要員計画の業務区分別の白い2行ラベル基準
  320〜650px）のまま変わらないこと、要員計画の業務区分別では白いラベル基準の高さとの
  大きい方になり既存の650px上限をツールチップの必要高さが上回る場合は上限を超えてよい
  こと、測定用に一時的に表示したツールチップが残らないこと（アクティブ要素が空に戻って
  いること）、拠点・月・表示月数・振替・雇用区分の切替等で内容が変わったときに再計算され、
  今の高さより低くならないことを確認します。
- `verify_sitesummary_headcount_labels.js` — 拠点サマリ「実績工数（業務区分別）」グラフ
  （`plansitesum2-combined`）の棒に「◯人」の人数ラベルを描画する
  `siteSummaryHeadcountLabelsPlugin()` の検証。(A) ラベルの描画自体
  （トップレベル関数のため`window`から直接呼べる）を手組みのデータセットに対して
  本物のChart.jsで描画させ、セグメントに収まる場合は中央・白文字、収まらない場合は
  棒の右側・薄い色になること、標準労働時間棒（3段）の合計ラベルが3段分まとめて1つだけ
  描画されること、0・無しの値は描画されないことを確認します。(B) 4種類の人数（実績棒・
  過去月／未来月の標準労働時間棒・新規要員・増減）の集計ルール自体
  （`renderSiteSummaryView()`内のローカル関数のため直接呼べず、`getActiveData()`等の
  本物のトップレベル関数を呼び出す形でテスト側に再現）を、拠点・雇用区分の絞り込みとの
  連動、実績はあるが標準労働時間シートと照合できない人の除外、退職予定者・新規要員の
  開始月条件、31・30・28日の月での人数換算（時間÷(8h×暦日数)、小数1桁）について確認
  します。(C) 人数ラベル用プラグインを追加した状態でも、`verify_plancompare_tooltip_height.js`
  ⑥-aと同じ再現条件・実マウスホバー方式で、PR #518のツールチップ切れ防止が引き続き
  機能することを確認します。
- `verify_sitesummary_headcount_total.js` — 同じグラフ（`plansitesum2-combined`）の棒に
  追加した、棒ごとの総合計人数ラベル（「計◯人」太字）の検証。(A) ラベルの描画自体
  （`siteSummaryHeadcountLabelsPlugin()`・`fitChartHeightForHeadcountTotals()`は
  トップレベル関数のため`window`から直接呼べる）を手組みのデータセットに対して本物の
  Chart.jsで描画させ、積み上げ列の一番上のセグメントのさらに上に太字で描かれること、
  そのセグメントの内訳ラベルが棒の上側に出ている場合はさらに1行分あけて描かれること、
  0・nullは描画しないこと、小数は小数1桁・整数は整数のまま表示されること、グラフの
  高さが足りない場合は`fitChartHeightForHeadcountTotals()`が必要な高さまで広げ、
  グラフ上端で切れず凡例とも重ならないことを確認します。(B) 総合計の数え方自体
  （実績棒は内訳(div別)の縦計と一致すること・絞り込みとの連動、標準労働時間棒は
  過去月が青系3段の合計、未来月が3段＋新規要員＋増減の合計になること、増減の小数を
  含む合算と丸め）を、`verify_sitesummary_headcount_labels.js`と同じ方針でテスト側に
  再現して確認します。(C) 総合計ラベル用の高さ調整を追加した状態でも、PR #518の
  ツールチップ切れ防止が引き続き機能することを実マウスホバー方式で確認します。
- `verify_shipping_actual_auto.js` — 出荷内訳（パック数・袋数・バラ数・付帯作業・合計(点数)）の
  実績の取得元を、整理済み_分析（PROD_GID）から月ごとに切り替えた変更の検証。
  2026/8までは整理済み_計画_更新（PLAN_GID）の「出荷内訳／実数計画」の行（「構成比」の行と
  取り違えないこと）、2026/9（`SHIPPING_AUTO_FROM`）〜境目月（`getActualCutoffMonth()`）は
  販売抽出シート(商品別)の実績タブから自動計算（計画_更新に値があっても使わない・付帯作業は「－」）、
  境目月より後は計画_更新の値のままになること、合計(点数)は全ての月でパック＋袋＋バラ
  （付帯作業・シートの合計(点数)の行は使わない）になること、整理済み_分析の値が使われないことを
  確認します。自動計算については、商品名による区分（「袋」を含む→袋、「バラ」を含む→バラ、
  それ以外・商品名が空欄→パック。袋とバラの両方を含む場合は袋）、暦月の範囲（8/31・11/1の列が
  9月・10月に混ざらない）、「個数」の行だけを使うこと（重量の行は使わない）、空欄・数字でない
  値の読み飛ばしとカンマの除去、見出しが見つからない場合の失敗を確認します。境目月が2026/10に
  進んだ場合に2026/10も自動計算になること、販売抽出シートの読み込みに失敗した場合（参照先一覧
  全体・1拠点の実績タブだけ）に自動計算の月だけ「－」になり他の月・他の画面は表示され、画面上部の
  アラート（`#shipping-actual-alerts`、既存の工数振替アラートと同じ`transfer-alert-box`）で
  知らせることを確認します。また、勤務実績＞生産実績、勤務実績＞標準工数(h)、予実＞予定標準工数(h)
  の過去月、予実＞生産計画の過去月（実数計画の行）で同じ値になること、予実＞予定標準工数(h)・
  予実＞生産計画の未来月の読み方が変わっていないことを、実際に各画面を描画して確認します。
  （整理済み_分析の廃止後は、整理済み_分析を読みに行かないことも確認します。prodDataが実績月
  だけになったため、境目月より後の月の取得元は、prodDataと同じ関数
  `computeShippingActualValues()` に境目月より後の月を渡して確認します。予実＞生産計画の
  構成比の行は、過去月が実績から計算した割合（小数2桁）・未来月がシートの値（小数2桁）で
  あることを確認します。）
- `verify_remove_prod_sheet.js` — 整理済み_分析（PROD_GID）への依存をなくした変更の検証。
  コード中に`PROD_GID`・整理済み_分析のgid・収穫量の補完処理（†）が残っていないこと、
  整理済み_分析を読みに行かないこと、勤務実績＞生産実績の表（prodData）の骨組みが
  整理済み_計画_更新から作られること（月＝1行目の見出しのうち整理済み_Mで判定した実績月と
  整理済み_Mの実績月、未来月は含まない／行＝拠点ごとに生産実績3行（南丹の「生販実績」も
  「生産実績」）→栽培内訳7行→出荷内訳5行）、各行の値が実績の取得元（菌床数集計・収穫管理表・
  売り上げ分析・出荷内訳）の値になり計画_更新の計画値は使われないこと、表の上の表示が
  取得元に合わせた表示になること、出荷内訳（実績）の下に「出荷内訳（構成比）」4行が追加され
  パック数・袋数・バラ数÷合計(点数)の小数2桁（付帯作業・合計(点数)が0の月は「—」）になること、
  URL_収穫管理表にURLが無い月の収穫量が「—」で†が出ないこと、計画_更新に菌床購入数(本)の
  行が無い拠点でも菌床購入数(本)の行が表示されることを確認します。予実＞生産計画では、
  カテゴリ列の見出しが行とずれない（付帯作業の行も構成比・計画のまとまりに入り、結合セルが
  5行分になる）こと、過去月（〜境目月）の全ての行が生産実績と同じ実績の値（構成比は実績の
  割合、構成比の付帯作業・合計(点数)は「—」）になり、未来月はシートの値のまま（構成比は
  小数2桁の表示）であることを確認します。勤務実績＞標準工数(h)・予実＞予定標準工数(h)の
  過去月が実績の値から計算した工数のままであること、予定標準工数(h)の未来月の読み方が
  変わっていないこと、整理済み_Mに2026/10が増えると2026/10も実績月になることも確認します。

## vendor/ フォルダについて

`vendor/chart.umd.js` は、work-hours.html が `<script src="https://cdn.jsdelivr.net/npm/chart.js@4.4.3/...">`
で読み込むのと同じバージョン（npmの `chart.js@4.4.3` の `dist/chart.umd.js`）を複製したものです。
テストはCDNへのリクエストをこのファイルの内容で差し替えて実行します。本体のバージョンを
更新した場合は、このファイルも合わせて更新してください。

## 公開対象からの除外について

`tests/work-hours/` は GitHub Pages（`.github/workflows/pages.yml` の `upload-pages-artifact` が
`dashboard` フォルダのみを対象にしている）および Firebase Hosting（`firebase.json` の
`hosting.public` が `dashboard` のみを指している）のどちらからも、もともと対象外です。
