# 椎茸 日々の過不足確認シート（shiitake-shipment-plan.html）のテスト

`dashboard/shiitake-shipment-plan.html` の動作確認用 Playwright テストです。
実際のスプレッドシート・保存先GASへのネットワークアクセスは行わず、`page.route()` で
CSV（`/export?format=csv`）・GASの応答をモックして検証します。

## 必要なパッケージ

- Node.js
- [Playwright](https://playwright.dev/)（`playwright` パッケージと Chromium 本体）

リポジトリに `playwright` が未インストールの場合は以下でインストールしてください。

```sh
npm install -D playwright
npx playwright install chromium
```

## テストの実行方法

1. リポジトリのルートで、`dashboard` フォルダをカレントにしたローカルサーバーを起動する（別ターミナル、またはバックグラウンド実行）。`tests/forecast/` のテストが同時に使う8811番とは別のポートを使う。

   ```sh
   python3 -m http.server 8812 --directory dashboard
   ```

2. テストを実行する（テストは `http://localhost:8812/shiitake-shipment-plan.html` にアクセスします）。

   ```sh
   node tests/shipment-plan/verify_shipment_plan_harvest_detail.js
   node tests/shipment-plan/verify_shipment_plan_detail_inabe_only.js
   node tests/shipment-plan/verify_shipment_plan_cell_selection.js
   node tests/shipment-plan/verify_shipment_plan_layout_state.js
   node tests/shipment-plan/verify_shipment_plan_gunma_panel1.js
   node tests/shipment-plan/verify_shipment_plan_gunma_panel23.js
   ```

   各行末に `: OK` / `: NG` が出力され、最後に `すべてOK` / `NGあり` と `DONE` が表示されれば実行完了です。
   終了コードは成功時 `0`、失敗時 `1` です。

## ファイルの内容

- `verify_shipment_plan_harvest_detail.js` — 収穫予測パネル（table2）・在庫予測パネル（table3）に追加した「詳細」（収穫見込の手入力）の検証。収穫見込×収穫比率でのサイズ別按分（秀・優はLの按分）、手入力が無い日は本体の表示値へのフォールバック、飛び飛びの入力（一部の日だけ手入力）・0kgの手入力の扱い、入力の確定（Enter・フォーカス移動）→即時再計算→保存、保存失敗時の赤枠・再送、全角数字・カンマ・kg付き入力の読み取りと不正値のエラー表示、在庫予測の詳細（収穫予測の詳細の値を使った当日〜8日後の積み上げ計算。収穫予測の詳細が「－」の日も0として最後まで計算を続ける点が本体とは異なる）、詳細パネルが最初は閉じていること、基準日・実績日・拠点の切替で古い読み込み結果を破棄すること（世代チェック）、本体（table1・table2・table3）の表示・計算がこの機能追加によって変わっていないことを確認します。拠点切替の確認は、いなべのまま切り替え直すケースのみ（群馬・南丹への切替時の挙動は `verify_shipment_plan_detail_inabe_only.js` が担当）。
- `verify_shipment_plan_detail_inabe_only.js` — 詳細は拠点を見て収穫見込GASに読み書きするため、群馬・南丹を選んだまま入力すると、本体の表示と食い違う拠点の実データ（直近工数計画・PR #503が使う収穫見込）を書き換えてしまう問題への対応を検証します。群馬・南丹を選んだときに、収穫見込GASへの読み込み・保存が一切発行されないこと、詳細の入力欄が無効になること、収穫予測・在庫予測の詳細の数値（実績・比率・日別・合計）がすべて「－」になること、「この画面は現在いなべのみ対応です。群馬・南丹の収穫見込は直近工数計画で入力してください。」の注記が表示されること、いなべに戻すと読み込み・入力・表示（手入力した値の復元を含む）が元どおりになることを確認します。あわせて、本体（table1〜3）が拠点トグルを切り替えても「常にいなべのデータを表示する」仕様ではなくなったこと（パネル1＝在庫・出荷予定が群馬でも実データで表示されるようになったこと）の回帰確認として、群馬を選ぶとtable1がいなべの数字のままでなくなること、群馬のtable2・3と南丹のtable1〜3が「－」＋「◯◯は準備中です」になること、いなべに戻すと元の実データ・注記なしに戻ることを確認します（パネル1が群馬の実データで正しく表示されることの検証自体は `verify_shipment_plan_gunma_panel1.js` が担当）。
- `verify_shipment_plan_cell_selection.js` — 表のセルの範囲選択と、選んだセルの集計を画面の一番下の帯に表示する機能（直近工数計画・PR #498 と同じ操作感）の検証。選べるのは在庫・出荷予定（table1）・収穫予測（table2）・在庫予測（table3）と、収穫予測・在庫予測の詳細の表の数字のセルで、見出し・サイズ名・収穫予測の詳細の合計の行の入力欄は選べないこと、ドラッグ（四角い範囲）・Shift＋クリック（範囲を広げる）・Ctrl／Cmd＋クリック（1セルずつ追加・解除、別の表のセルも追加できる）・スマートフォンのタップ（1セルずつ追加・解除）で選べ、ドラッグ・Shiftの範囲は同じ表の中だけであること、選んだセルの色、ドラッグ中に文字選択が起きないこと、帯の合計・平均・個数・最小・最大（kgは小数1桁、比率は小数2桁）、「－」・空欄は数えず「0.0」は0として数えること、kgと比率の混在・合計の行とサイズの行・Lと秀・優の二重計上の注意表示、帯の高さ（幅1280pxで1行分）とページの一番下の行（詳細を開いた状態を含む）が帯に隠れないこと、帯に隠れる位置（画面の一番下の行）からのドラッグ、「選択を解除」・Esc・表の外のクリックでの解除、基準日・実績日・拠点の切り替えと詳細の再計算で選択が解除されること、詳細を開閉しても他の表の選択が残ること、収穫見込の入力・保存がこれまでどおり動くことを確認します。
- `verify_shipment_plan_layout_state.js` — タイトル部分（タイトル・拠点ボタン・下の罫線）の画面上部への固定、表の行の高さを約10%詰めたこと、表示状態（拠点・詳細の開閉）のURLのクエリへの保持の検証。幅1280px・375pxで、固定部分がスクロールしても画面の上に残り、ページと同じ背景色で塗られて下を流れるパネル・表より手前に描かれること、基準日・実績日の操作欄は固定されずパネルと一緒にスクロールすること、スクロールした状態でも拠点ボタンが押せることを確認します。行の高さは、変更前の余白に戻すスタイルを一時的に足して同じ画面で変更前の高さを測り、見出しの行・データの行とも0.88〜0.92倍（収穫予測の詳細の合計の行（入力欄）は0.85〜0.95倍）であること、文字の大きさ・列の幅・色が変わらないこと、入力欄に入力・保存できることを確認します。表示状態は、拠点の切り替え・詳細の開閉で `?site=群馬&harvestDetail=open&stockDetail=open` のようにURLが書き換わり（履歴は増えない）、リロードで同じ状態に戻ること、いなべ・詳細を閉じた状態ではクエリが無くなること、クエリが無い・値がおかしいときは いなべ・詳細を閉じた状態になること、群馬・南丹の状態でリロード（クエリで直接開く）しても収穫見込GASへの読み込み・保存が送られず入力欄が無効のまま（PR #515 の安全策）であること、htmlpreview形式のURL（`?https://github.com/…/shiitake-shipment-plan.html`）でも表示するファイルのURLを壊さずに状態を保てることを確認します。基準日・実績日も `base=2026-11-10`・`actual=2026-11-13` のようにクエリへ反映され（既定の今日・前日のときは付かない）、リロードや翌日（テストでは「今日」を1日進めて再現）に開き直してもその日付のまま表示されること、「今日」「前日」ボタンで既定に戻りクエリから消えること、おかしな日付（実在しない・今日より先・古すぎる・形式違い）はその日付だけ既定に戻り他方・拠点・詳細は保たれることを確認します。あわせて、スクロールした状態での範囲選択（ドラッグ・Shift・Ctrl・タップ）と集計の帯、固定したタイトル部分の上のクリックで下の表のセルが選ばれないことを確認します。
- `verify_shipment_plan_gunma_panel1.js` — 在庫・出荷予定パネル（table1）を群馬でも実データで表示できるようにした対応の検証。`?site=群馬` で直接開いたとき、URL_在庫管理表（DB共有シートのタブ）から群馬の在庫管理表（椎茸在庫管理表(安中)）のURLを解決して読み、M・L・2L・袋の製品在庫・生在庫、秀・優の生在庫（L生在庫の比率表記から）・製品在庫（転写_秀優_判別タブの按分ルールから）、合計行が目安どおりの値（M 11.7/420.0、L 72.3/212.8、秀 41.1/85.1、優 31.2/127.7、2L 138.4/502.0、袋 96.0/391.0、合計 318.4/1,525.8）になること、群馬の行名に含まれる全角Ｍ・Ｌ（Ｍ製品在庫・Ｌ製品在庫）も半角と同じ行として見つけられることを確認します。出荷予定は、販売予実抽出シートの受注計画がいなべより28列右（AY〜BB列）にあることを踏まえて読み、秀・優は群馬_受注タブから読むことを確認します。拠点の切替では、いなべ→群馬→いなべと切り替えたときに表示が正しく描き直されること、群馬の読み込みが遅れている間にいなべへ戻した場合に遅れて届いた群馬の値でいなべの表示を上書きしない（世代番号での保護）ことを確認します。URL_在庫管理表に群馬の欄が空のときは全サイズが「－」になり、「URL_在庫管理表に群馬の在庫管理表がありません」の注記が出ることを確認します。あわせて、簡易なモックで、群馬のパネル2・3（収穫予測・在庫予測）がもう「準備中」のプレースホルダー扱いでなくなったこと（南丹のパネル1〜3は引き続き「－」＋「◯◯は準備中です」のままであること）を確認します（パネル2・3の実データの値そのものの検証は `verify_shipment_plan_gunma_panel23.js` が担当）。
- `verify_shipment_plan_gunma_panel23.js` — 収穫予測パネル（table2）・在庫予測パネル（table3）を群馬でも実データで表示できるようにした対応の検証。基準日2026-10-28・実績日2026-10-27で、URL_収穫管理表（DB共有シートのタブ）から群馬の「収獲目標値(合計)」ファイルのURLを解決して読み、M・L・2L・袋の収穫実績・収穫比率、秀・優の実績（収穫_秀優比率の40/60をLの実績に按分。拠点の区別が無く群馬もいなべと同じ比率を使うこと）が目安どおりの値（M 66.3、L 206.4、秀 82.5、優 123.8、2L 248.7、袋 157.8。按分前の合計は679.05）になることを確認します。日別の収穫予測は、群馬の「転写」タブ（B1が「見込み1」で年月の列がそれより右にあることを含む）の日別合計×比率で、10/28〜11/1の5日分が目安どおりの値になること、月をまたいだ列（2026.10→2026.11）の切替が正しく行われること、転写に値が無い日（11/2以降）は「－」になることを確認します。在庫予測は、在庫・出荷予定パネル（table1）の製品在庫＋生在庫を在庫実績とし、当日〜2日後が「在庫実績＋収穫予測－出荷予定」の積み上げで正しく計算されることを確認します。拠点の切替・実績日の変更では、いなべ→群馬→いなべの描き直し、群馬の読み込みが遅れている間にいなべへ戻しても上書きされないこと（世代番号での保護）、実績日を変更すると変更後の日の実績に描き直されることを確認します。あわせて、南丹のパネル1〜3が引き続き「－」＋「南丹は準備中です」になること、群馬のパネル2・3に「準備中」の注記が出ないこと、URL_収穫管理表の群馬の欄が空の月は群馬の実績・比率・予測が「－」になる（パネル1には影響しない）ことを確認します。

いずれのファイルも、CSVモックの組み立てや日付固定（`fixTodayTo`）などの補助関数をファイル内に直接含んでおり、他ファイルへの依存はありません。

## 公開対象からの除外について

`tests/shipment-plan/` は、GitHub Pages（`.github/workflows/pages.yml` の `upload-pages-artifact` が `dashboard` フォルダのみを対象にしている）および Firebase Hosting（`firebase.json` の `hosting.public` が `dashboard` のみを指している）のどちらからも、もともと対象外です。追加の除外設定は不要でした。

GitHub Actionsの `validate` ジョブ（`pages.yml`）は `dashboard/*.html` のみを対象にJS構文チェックを行うため、`tests/shipment-plan/` 配下のファイルで失敗することはありません（テストを自動実行する設定にもなっていません）。
